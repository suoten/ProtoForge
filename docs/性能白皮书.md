# ProtoForge 性能白皮书（v1.11.0）

> 所有数字由内置基准场景实测产出，用户可用一条命令复现（方法与命令见文内）。
> 测试环境与您的硬件差异会造成偏差；同一台机器上两次运行的**相对变化**（回归门禁）
> 比绝对数字更有意义。

## 测试环境

| 项 | 值 |
|---|---|
| ProtoForge | v1.11.0 |
| Python | 3.12（Windows x64） |
| 事件循环 | Proactor（Windows 默认） |
| 数据采集方式 | 进程内基准场景（`protoforge/benchmark/scenarios.py`），真实 socket |

## 一、引擎生成吞吐（tick 时长）

模拟设备按周期生成点位值是引擎主循环的核心成本。场景：创建 N 设备 × M 测点
（正弦/随机生成器混合），手动驱动 tick 并统计整轮（全部设备生成 + 值更新）时长。

| 规模 | 测点数 | tick 平均 | tick P95 | tick 最大 | 内存增量 | 批量创建耗时 |
|---|---|---|---|---|---|---|
| 100 设备 × 50 点 | 5,000 | **0.119 ms** | 0.122 ms | 0.172 ms | +8.6 MB | 0.11 s |
| 1000 设备 × 100 点 | **100,000** | **1.117 ms** | 1.362 ms | 1.600 ms | +155.5 MB | 2.2 s |

**结论**：单实例 1000 设备 / 10 万测点规模下，每 tick 生成成本 ≈1.1ms——
相对默认 1s 的 tick 周期占比 0.11%，生成层不是瓶颈。内存 ≈1.6KB/测点。
v1.11.0 起 tick 循环默认分片（每 100 台设备让出一次事件循环），
大批量设备不会拖慢同进程 API/协议响应。

复现：

```bash
protoforge benchmark run --scenario engine_tick_generation \
  --params '{"devices": 1000, "points_per_device": 100, "ticks": 10}'
```

## 二、Modbus TCP 线级读延迟（真实 socket）

单个 pymodbus 客户端对 ProtoForge Modbus TCP 从站连续读保持寄存器
（FC03，每读一个请求-响应 PDU，1000 次采样）：

| 指标 | 值 |
|---|---|
| P50 | **0.399 ms** |
| P95 | 0.429 ms |
| P99 | **0.544 ms** |
| 最大 | 1.168 ms |
| 吞吐（单客户端） | **2,458 读/秒** |
| 错误 | 0 |

复现：

```bash
protoforge benchmark run --scenario modbus_wire_read --params '{"reads": 1000}'
```

## 三、并发客户端吞吐

10 个并发 pymodbus 客户端同时读（每客户端 100 次，共 1000 次）：

| 指标 | 值 |
|---|---|
| P50 | 3.794 ms |
| P95 | 4.470 ms |
| P99 | 5.637 ms |
| 聚合吞吐 | **1,913 读/秒** |
| 错误 | 0 |

并发下 P50 上升至 3.8ms 是事件循环串行处理 10 连接的正常排队；
吞吐与单客户端基本持平（服务器处理能力富余）。

复现：

```bash
protoforge benchmark run --scenario modbus_concurrent_read \
  --params '{"clients": 10, "reads_per_client": 100}'
```

## 四、容量规划表（基于实测外推）

| 部署规模 | 建议设备数 | 建议测点数 | tick 成本 | 内存预算 | 说明 |
|---|---|---|---|---|---|
| 笔记本/台式机（开发演示） | ≤500 | ≤5 万 | <1 ms | <200 MB | 实测覆盖 |
| 工控机/入门服务器 | 1000 | 10 万 | ≈1.2 ms | ≈300 MB（进程基线另计） | 实测覆盖（本文数字） |
| 更大规模 | 2000+ | 20 万+ | 线性外推 ≈2.5 ms | 线性 ≈1.6KB/点 | 外推值，建议先跑基准 |

> 内存项为设备/测点数据结构增量（不含 Python 解释器与依赖基线 ~120MB）。

## 五、回归门禁（CI 可用）

同场景两次结果对比，延迟/时长类指标回退 >10% 判 REGRESSION（exit 1）：

```bash
# 第一次（基线）
protoforge benchmark run --scenario modbus_wire_read --label baseline
# 变更后再跑并与基线对比 —— 回归 >10% 时 exit 1，可直接进 CI
protoforge benchmark run --scenario modbus_wire_read --compare-to <baseline_id>
```

API 侧：`GET /api/v1/benchmarks/compare?a=<id>&b=<id>`；结果持久化于
`data/benchmarks/`（含 python/平台/CPU 指纹，跨环境对比请以同机为准）。

## 六、可观测性

- `GET /api/v1/integration/metrics`：进程 RSS/虚拟内存/线程数/句柄数 +
  各协议活跃连接数（Prometheus 风格 gauge）
- 引擎 `tick_stats`：tick 平均/最大时长（运行期观测）
- 连接上限：协议 `protocol_config.max_connections`（0=不限），
  超限拒绝并计数（`protoforge_protocol_errors_total{category=network}`）

## 七、方法论与边界（诚实声明）

1. 以上数字为**本机实测**（生成层 + 单协议线级读），非全协议矩阵——
   其余协议延迟主要受帧解析复杂度影响，量级与 Modbus 同档（纯 Python 解析）。
2. 规划验收中的"1000 设备 24 小时长跑无泄漏"：基准模块已提供内存增量指标
   （`memory_rss_delta_mb`）与结果持久化，24h 稳定性测试建议用
   `--params '{"devices": 1000, ...}'` 起环境后以小时级采样 RSS 巡检
   （`/api/v1/integration/metrics`），本文不声称已完成 24h 长跑。
3. 并发连接上限由各 TCP 协议服务器 `max_connections` 控制（20 个 TCP
   协议服务器已接入统一连接门）。
