# RTU over TCP：为什么"两种帧"要分两个端口

> "RTU over TCP" 这个词在工控圈有两层含义，混用是联调翻车的头号来源。
> 本文说清这两种帧的差别、ProtoForge 的端口约定，以及排障思路。

## 问题的根源：一个词，两种话

串口设备（Modbus RTU）联网后，数据怎么走 TCP？业界有两种完全不同的做法：

**做法一：MBAP 包着 RTU 数据区（Modbus TCP 本身）**

客户端说的是标准 Modbus TCP/MBAP 帧——事务标识符 + 协议标识 + 长度头，功能码和寄存器语义与 RTU 一致，但没有 CRC（MBAP 头里有长度校验）。Kepware 的 Modbus TCP 驱动、绝大多数组态软件的"Modbus TCP/TCP 驱动"说的都是这种话。

**做法二：RTU 帧原封不动直走 TCP**

把串口线换成网线：完整的 RTU 帧（地址 + 功能码 + 数据 + **CRC16**）直接塞进 TCP 流，没有任何额外头。典型来源：pymodbus 客户端 `framer=RTU` 直连 TCP、NPort/USR-TCP232 等串口服务器的"透传模式"。

两种做法**在 TCP 层都能"连上"**，但帧格式完全不兼容——MBAP 客户端连到 RTU 帧端口（或反过来），结果是"TCP 三次握手成功，然后数据全部对不上"，表现为无响应或读到乱值。这是"能连上但读不对"的最常见根因。

## ProtoForge 的端口约定（v1.16.2 起）

设备高级配置的 **Link Mode** 三选一，按"客户端会说哪种话"来选：

| 客户端形态 | 模式 | 默认端口 |
|---|---|---|
| Modbus TCP/MBAP 客户端（Kepware/组态 TCP 驱动） | `tcp_bridge` | 5021 |
| RTU 帧直走 TCP（pymodbus framer=RTU、串口服务器透传） | `rtu_over_tcp` | 5022 |
| 真串口/虚拟串口（com0com 等） | `serial` | COM 口 |

要点：

- **`rtu_over_tcp` 的帧处理与串口模式完全一致**——CRC 校验、错位重同步、广播语义全部保留，只换了传输层。也就是说，串口从站该有的"脏"行为（半帧、干扰错位）在 TCP 透传场景下同样被正确处理。
- 两种 TCP 模式分开设两个端口（5021/5022），就是为了**让服务端从端口就知道客户端说什么话**，不需要逐帧嗅探猜测，也避免同一端口上两种帧互相污染。
- 三个模式的数据区（寄存器/线圈）完全同源——HMI 侧从"Modbus RTU 串口"换成"Modbus TCP"或"RTU over TCP"，点表一个字不用改。

## 版本演进与一个真实的配置坑

- v1.11.1 引入 `tcp_bridge`（MBAP 桥接），解决了"没有串口也能服务 RTU 数据区"的需求；
- 用户随后提出：pymodbus `framer=RTU` 和串口服务器透传场景，客户端发的是带 CRC 的裸 RTU 帧——严格意义的 RTU over TCP 此前不支持。v1.16.2 补上 `rtu_over_tcp`，并经 pymodbus RTU-framer 客户端直连读写、ProtoForge 自家主站互连双重验证。
- v1.16.3 修复了一个配置歧义：界面上"表单 Link Mode"和"高级配置 mode"两个入口可以保存出互相矛盾的值（表单填了 `rtu_over_tcp:5022`，设备实际存的还是旧的 `tcp_bridge:5021`，于是从站监听在 5021 而客户端连 5022，怎么都"连不上"）。新版保存时自动按 Link Mode 清理互斥字段。

## 排障清单

"RTU over TCP 连不上/读不对"按顺序查：

1. **客户端到底说哪种话？** MBAP（有事务 ID 头）还是裸 RTU 帧（尾部有 CRC）？抓一帧报文一眼可辨，或直接用 [报文解析接口](../README.md#-开发调试) 逐字段展开。
2. **端口对不对？** 5021 只说 MBAP，5022 只说 RTU 帧。连错端口的典型症状就是"TCP 通，业务无响应"。
3. **改完配置重启协议服务没有？** Link Mode 是启动参数，改完必须**停止再启动**才生效。
4. **设备配置里 mode 和表单 Link Mode 是否打架？** 升级到 v1.16.3+ 可避免此坑；旧版本手动确认两处一致。
5. 还不通：`raw_frames` 开帧日志，导出报文逐字节对。
