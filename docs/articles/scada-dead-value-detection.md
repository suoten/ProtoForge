# 组态软件"死值检测"与仿真环境：一个被误报为"通讯故障"的假 Bug

> 现象：MCGS 组态画面报"通讯错误"，但在仿真器里改一下数据就恢复正常了。
> 真相：链路一直是通的，这不是通讯故障，是组态软件的**死值检测**机制在和仿真环境"打架"。
> 这个坑在真实联调中反复出现，值得单独写一篇。

## 现象还原

某次汇川 HMI/组态联调：仿真从站链路已通、地址已对齐，画面上却间歇性报通讯异常。关键线索是——**在仿真器里手动改一下该点位的值，报错立刻消失**，过一会儿数据不变了又报。

## 根因

组态软件/HMI 普遍带"死值检测"（数值不变监视）机制：某个数值长时间不变，保守起见报一个异常，提醒工程师"这个值是不是冻结了"（比如传感器卡死、变送器故障）。

这个功能在真实现场非常有用——真实传感器的值天然带噪声，长时间纹丝不动几乎一定是故障。但仿真环境里，如果把点位配成"固定值"生成器，值天生不变，就正好撞上这个检测，被误判为通讯异常。

## 解法（二选一）

**解法一（推荐）：让值动起来**

在 ProtoForge 设备测点里，把该点的生成器从"固定值"改成"随机"，范围设小一点（如 min=当前值-0.5、max=当前值+0.5）。值会轻微波动：

- 组态软件永远不会报死值异常；
- 更接近真实传感器的行为，画面趋势图也更好看；
- v1.8.6 起，布尔点位的随机生成器是 0/1 翻转，布尔点同样适用（布尔不需要 min/max）。

**解法二：关掉组态侧的检测**

MCGS 等组态软件的设备组态里有"数值不变处理/死值报警"相关选项，测试场景直接关掉。缺点：每台 HMI/每个工程都要单独关，且如果后续还要测死值告警联动本身，这个开关就动不了。

## 排查要点：怎么区分"真通讯错误"和"死值误报"

| 判据 | 真通讯错误 | 死值误报 |
|---|---|---|
| 从站应答 | 返回异常码（如 Illegal Data Address）或超时 | 完全正常应答 |
| 手动改值后 | 不一定恢复 | **立刻恢复**（值变了就不触发检测） |
| 客户端报错文案 | Illegal Data Address / Timeout 等 | "数值长时间不变/死值"类描述 |

排查顺序：先看客户端报错文案和仿真器帧日志（有无异常码），确认链路正常后，再考虑死值检测。

## 顺带一提：生成器怎么选

| 生成方式 | 适用场景 |
|---|---|
| 固定值 | 回归测试断言、给对接方一个明确的"预期值" |
| 随机（小范围） | 长时间挂着的 HMI 画面/趋势图，模拟真实传感器噪声 |
| 随机（大范围）/正弦 | 测试曲线形态、报警阈值联动 |
| 脚本 | 特定业务逻辑（如按时间步进的水位） |

一句话：**仿真值"太完美"本身就是不真实**——真实设备的值永远在抖，让仿真也抖起来，很多"假故障"自然消失。
